# FeedForge — 개인 관심도 기반 큐레이션 피드 서비스

> 상태: 검토 대기 (v2 승인 후 착수)
>
> 변경 요약: 웹 피드를 주 사용 공간으로, Telegram을 보조 알림 채널로 변경한다.
> 프런트엔드는 React(Vite) + Tailwind CSS + shadcn/ui로 확정한다.

## 1. 개요

핫딜 / GitHub trending / 테크·AI 뉴스를 주기적으로 수집하고,
개인 관심도 프로필과 대조해 관련성이 높은 항목을 웹 피드에 제공한다.

사용자는 웹에서 항목을 확인하고 좋아요·싫어요 피드백을 남긴다.
피드백은 관심도 프로필에 반영되어 추천이 개인 취향에 맞게 조정된다.

Telegram은 추천 항목 전체를 전달하는 수단이 아니라,
놓치면 아쉬운 중요 항목만 알려주는 보조 알림 채널로 사용한다.

핵심 가치

- 개인화: 모든 수집 항목이 아니라 관심에 맞는 항목을 보여준다.
- 편리한 피드백: 웹에서 여러 항목을 확인하고 간편하게 평가한다.
- 학습: 명시적 피드백이 이후 추천에 반영된다.
- 선택적 알림: 웹에 방문하지 않아도 중요한 항목은 놓치지 않는다.

> 찾아보면 내 관심에 맞는 피드가 준비되어 있고,
> 놓치면 아쉬운 항목만 먼저 알려준다.

## 2. 서비스 범위

### 2.1. v1 전제

- 단일 사용자용 개인 서비스로 시작한다.
- 웹 피드를 주 인터페이스로 제공한다.
- 모바일 브라우저에서도 사용 가능한 반응형 화면을 제공한다.
- Telegram 알림을 꺼도 수집·추천·피드백은 정상 동작한다.
- 추천은 키워드·카테고리 기반으로 시작한다.
- LLM 분류, 임베딩, 벡터 DB, 별도 메시지 큐는 도입하지 않는다.

### 2.2. 채널별 역할

| 기능 | 웹 | Telegram |
|---|---|---|
| 추천 확인 | 개인화 피드 | 중요 항목 알림 |
| 좋아요 / 싫어요 | 주 피드백 수단 | 후순위 선택 기능 |
| 이전 항목 탐색 | 필터·히스토리 | 웹 링크로 이동 |
| 관심도 관리 | 관심·제외 키워드 관리 | 제공하지 않음 |
| 알림 설정 | 활성화·상한·조용한 시간 | 설정에 따라 수신 |

## 3. 기술 스택

|---|---|---|

| Telegram | Bot API 직접 호출 | 전용 bot은 후순위 (TODO, 9.1절) |

디자인 토큰(CSS 변수)·컴포넌트 규칙은 개인 design-system 컨벤션을 따른다.

배포는 기존 서버 패턴대로 UI 컨테이너를 분리한다
(scoophub-ui, gonamu-cineseek-ui와 동일 구성 — nginx가 빌드 산출물 제공,
`/api/*`는 Spring Boot 앱으로 프록시).

## 4. 아키텍처

```
┌──────────────────────────────────────────────────────┐
│                  Spring Boot App                     │
│                                                      │

│                                                      │
│  ScoringService                                      │
│    └─ 관심도 프로필 대조                              │
│       → 추천 후보 평가 → FeedItem 저장                │
│                                                      │
│  Web / REST API (/api/*)                             │
│    ├─ 추천 피드 조회                                  │

│  NotificationJob                                     │
│    └─ 높은 점수의 추천만 선별                         │
│       → 발송 대기 저장 → Telegram 발송                │
└────────────────────────┬─────────────────────────────┘
                         │ 5432 (기존 컨테이너)
                ┌────────┴────────┐
                │  feedforge DB   │
                └─────────────────┘

┌──────────────────────────────────────────────────────┐
│              feedforge-ui (React SPA)                │
│  Vite 빌드 산출물을 nginx 컨테이너가 제공             │
│  /api/* → Spring Boot 앱으로 프록시                   │
└──────────────────────────────────────────────────────┘
```

### 설계 원칙

- 수집, 추천, 알림을 분리한다.
- 웹 추천 여부와 Telegram 발송 여부를 별도로 관리한다.
- 외부 HTTP 호출 중 긴 DB 트랜잭션을 유지하지 않는다.
- 수집기 하나의 실패가 다른 소스의 수집을 막지 않게 한다.
- 추천 후보를 모아 평가한 뒤 알림을 선정한다.
- 특정 소스의 수집 순서가 일일 알림 예산을 독점하지 않게 한다.

배포는 기존 docker compose에 앱 서비스와 UI 서비스를 추가하고,
PostgreSQL은 기존 컨테이너를 공유한다.

## 6. 웹 화면

### 6.1. 추천 피드 — 메인 화면

웹에서도 전체 수집 목록이 아니라 **개인화된 추천 목록**을 기본 제공한다.

주요 기능

- 추천순 / 최신순 정렬
- 전체 / 핫딜 / GitHub / 뉴스 필터
- 원문 이동
- 좋아요 / 싫어요 / 피드백 취소
- 현재 피드백 상태 표시
- 추천 이유 표시
- 페이지네이션 또는 더 보기
- 모바일 반응형 레이아웃

카드 예시

```
WD SN850X 2TB — 149,000원
알구더 · 무료배송 · 20분 전
추천 이유: SSD, 저장장치 관심
[원문 보기] [👍 관심 있음] [👎 관심 없음]
```

동작 정책

- 피드백은 화면에 즉시 반영한다.
- 싫어요 항목은 기본 피드에서 숨긴다.
- 숨긴 항목은 별도 필터에서 확인하고 피드백을 취소할 수 있다.
- 딜 종료·품절 정보가 확인되면 카드에 표시한다.
- 내부 추천 점수는 상세 정보로 제공하고, 기본 화면에서는 추천 이유를 강조한다.

### 6.2. 좋아요 목록

- 좋아요한 항목 모아보기
- 소스 / 콘텐츠 유형 필터
- 원문 이동
- 좋아요 취소

v1에서는 별도 북마크를 만들지 않는다.
추후 "관심 있음"과 "나중에 보기"를 구분할 필요가 생기면 분리한다.

### 6.3. 관심도 및 알림 설정

- 관심 키워드 추가 / 삭제
- 제외 키워드 관리
- 카테고리 가중치 관리
- 필요 시 학습값 초기화
- Telegram 알림 활성화 / 비활성화
- 알림 임계치 / 일일 상한
- 조용한 시간 설정

## 7. 데이터 모델

아래는 논리 모델 초안이며, 실제 타입과 인덱스는 마이그레이션 작성 시 확정한다.

```sql
-- 수집 원본
raw_item (
  id,
  source,                 -- ZOD | FMKOREA | ARCA | GITHUB | NEWS
  provider,               -- 뉴스 매체 등 실제 공급자 구분
  source_key,
  category,
  title,
  url,
  canonical_url,
  extra JSONB,
  item_at,                -- 확인 가능한 원본 게시 시각
  first_seen_at,
  last_seen_at,
  updated_at,
  availability,           -- UNKNOWN | AVAILABLE | ENDED
  UNIQUE(source, provider, source_key)
)

-- 관심도 프로필
interest_profile (
  id,
  kind,                   -- KEYWORD | CATEGORY | SOURCE
  value,
  seed_weight,            -- 수동 설정 기준값
  learned_weight,         -- 피드백에 의한 변화량
  updated_at,
  UNIQUE(kind, value)
)

-- 웹 추천 결과
feed_item (
  id,
  raw_item_id,
  score,
  matched_terms JSONB,    -- 매칭 항목·당시 가중치·점수 기여도
  scoring_version,
  recommended_at,
  evaluated_at,
  expires_at,
  UNIQUE(raw_item_id)
)

-- 현재 피드백 상태
item_feedback (
  id,
  feed_item_id,
  kind,                   -- LIKE | DISLIKE
  channel,                -- WEB | TELEGRAM
  created_at,
  updated_at,
  UNIQUE(feed_item_id)
)

-- Telegram 발송 상태 및 이력
notification_delivery (
  id,
  feed_item_id,
  channel,
  status,                 -- PENDING | SENDING | SENT | FAILED | UNKNOWN | EXPIRED
  score_at_selection,
  attempt_count,
  next_attempt_at,
  last_error,
  telegram_chat_id,
  telegram_message_id,
  created_at,
  sent_at,
  UNIQUE(feed_item_id, channel)
)

-- 피드백 변경 및 학습 이력
feedback_log (
  id,
  feedback_event_id,
  feed_item_id,
  profile_id,
  previous_kind,
  new_kind,
  delta,
  previous_weight,
  new_weight,
  reason,
  created_at,
  UNIQUE(feedback_event_id, profile_id)
)

-- 단일 사용자 알림 설정
notification_settings (
  id,
  telegram_enabled,
  telegram_chat_id,
  score_threshold,
  daily_limit,
  quiet_hours_start,
  quiet_hours_end,
  timezone
)
```

### 모델 정책

- `provider`는 필수값으로 정규화해 고유 제약에 NULL이 들어가지 않게 한다.
- 동일 원본을 다시 수집하면 추천수·가격·상태 등 변경 가능한 필드를 갱신한다.
- 추천 항목의 점수는 갱신할 수 있지만, 이미 발송한 항목은 다시 발송하지 않는다.
- 피드백 취소 시 현재 상태를 제거하고 변경 이력을 남긴다.
- 매칭된 프로필 항목이 없는 피드백도 `profile_id` NULL·`delta` 0으로 이력 1건을 남긴다.
- 현재 모델은 단일 사용자 전제다.
- 다중 사용자 확장 시 프로필·추천·피드백·알림 설정에 사용자 식별자를 추가한다.

## 8. 스코어링 규칙

### 8.1. 기본 방식

```
score(item)
  = 매칭된 키워드 가중치 합
  + 매칭된 카테고리 가중치
  + 소스 가중치
  + 소스별 인기 보너스
```

추천 조건

- 관심 키워드 또는 관심 카테고리가 하나 이상 매칭되어야 한다.
  단, 콜드스타트 온보딩(8.3) 동안에는 인기 기반 노출로 대체한다.
- 총점이 웹 추천 임계치 이상이어야 한다.
- 제외 규칙과 신선도 조건을 통과해야 한다.

초기 정책

- 종자 프로필 없이 시작한다 (콜드스타트 — 아래 8.3 참조)
- 웹 추천 임계치: 3.0을 임시 시작값으로 사용
- 웹에서 추가한 키워드의 기본 seed_weight는 임계치와 함께 확정 (14절)
- 인기 보너스: 소스별 계수와 상한 적용
- 동일 관심 항목은 한 게시물에서 한 번만 가산
- 영문 짧은 키워드는 단순 부분 문자열 대신 토큰 경계 매칭
- 동의어는 소규모 사전으로 시작
- 소스 가중치는 v1에서 수동 관리

임계치는 관찰 모드 결과와 실제 피드백 패턴을 보고 조정한다.

### 8.2. 피드백 학습

| 입력 | 처리 |
|---|---|
| 좋아요 | 매칭된 관심 항목 강화 |
| 싫어요 | 매칭된 관심 항목 약화 |
| 취소 | 기존 피드백의 학습 효과 되돌리기 |
| 무반응 | 변화 없음 |
| 조회 / 원문 클릭 | v1에서는 학습에 사용하지 않음 |

- 좋아요·싫어요의 초기 총 변화량은 각각 +0.5, -0.5를 검토한다.
- 여러 프로필 항목이 매칭되면 총 변화량을 나누어 적용한다.
- 유효 가중치에는 상한과 하한을 둔다.
- 학습 대상은 키워드·카테고리이며, 소스 가중치는 자동 변경하지 않는다.
- 피드백 변경 시 이전 효과를 되돌린 후 새 효과를 적용한다.
- 학습 이력에는 실제 적용된 변화량을 기록한다.
- 같은 피드백을 반복 제출해도 추가 학습하지 않는다.
- 피드백 상태 변경과 프로필 갱신은 같은 트랜잭션에서 처리한다.

무반응을 싫어요로 간주하지 않는다.

장기 시간 감쇠가 필요해지면 게시물별 무반응 패널티 대신
학습값이 종자값으로 천천히 복귀하는 방식을 별도 검토한다.

### 8.3. 콜드스타트 (종자 프로필 없이 시작)

초기 키워드 없이 시작하므로 프로필이 형성될 때까지 별도 동작이 필요하다.

- 온보딩 단계: 관심 키워드·카테고리를 웹 설정 화면에서 직접 추가한다.
  추가된 키워드는 seed_weight로 등록되고 즉시 스코어링에 반영된다.
- 프로필 항목이 부족한 동안(예: 관심 항목 5개 미만)은
  인기 보너스(추천수·스타 증가량) 기준 피드를 함께 노출해
  피드백을 남길 소재를 제공한다.
  이 항목은 웹 추천 임계치 대신 소스별 인기 상위 기준으로 선정하고,
  추천 이유를 "인기 항목"으로 표시한다.
- 노출된 항목에 좋아요·싫어요를 남기면 매칭된 키워드·카테고리 후보가
  자동으로 프로필에 추가되는 방식을 검토한다 (명시적 확인 절차 포함).
- 온보딩 단계의 인기 기반 노출은 프로필 형성 후 자동 축소한다.
- 가중치 조정은 웹 설정 화면에서 수동으로도 가능하다 (6.3절).

## 9. Telegram 알림

### 9.1. 기본 정책

- 전용 bot을 신규 생성한다 (TODO — 후순위, 14절 참조).
- 웹 추천보다 높은 별도 알림 임계치를 사용한다.
- 하루 3~5개 수준에서 시작하고 운영 결과에 따라 조정한다.
- 일일 상한은 설정된 시간대 기준으로 계산한다.
- 조용한 시간에는 발송하지 않는다.
- 웹에서 이미 피드백한 항목은 발송 후보에서 제외한다.
- 품절·종료·오래된 핫딜은 발송하지 않는다.
- 최초 수집에서 과거 항목을 대량 발송하지 않는다.

### 9.2. 메시지 구성

- 제목
- 가격·배송비 등 핵심 정보
- 소스
- 짧은 추천 이유
- 원문 링크
- 웹 피드 항목 링크

v1에서는 Telegram 피드백 버튼 없이 시작할 수 있다.
추가할 경우 네이티브 리액션 수집 대신 인라인 버튼을 사용하고,
웹과 동일한 피드백 처리 로직에 연결한다.

### 9.3. 발송 신뢰성

- 발송 전에 DB에 대기 상태를 저장한다.
- 발송 작업은 대기 항목을 선점한 뒤 처리한다.
- 확실한 실패와 결과 불명확 상태를 구분한다.
- 재시도 가능한 실패에는 backoff를 적용한다.
- 결과가 불명확한 UNKNOWN 상태는 자동 재발송하지 않는다.

Telegram 발송과 DB 저장을 하나의 원자적 트랜잭션으로 묶을 수 없으므로,
외부 발송의 정확히 한 번 실행을 보장한다고 표현하지 않는다.

개인용 v1에서는 일부 누락보다 중복 알림을 피하는 정책을 우선한다.

## 10. 중복 및 신선도 정책

### 원본 중복

- 소스·공급자·원본 키로 중복 제거
- 재수집 시 최신 메타데이터 갱신

### 소스 간 동일 딜

- 정규화한 동일 구매 링크부터 중복 판정
- 제목·가격 기반 판정은 보수적으로 적용
- 상품 옵션이나 판매처가 다른 항목을 잘못 합치지 않도록 주의
- 동일 딜의 짧은 기간 내 중복 알림 억제

### GitHub

- v1에서는 저장소별 최초 한 번만 추천·알림
- 기간 경과 후 재급상승 재추천은 후순위

### 최초 실행

- 기존 항목을 기준선으로 수집한다.
- 과거 항목을 일괄 알림하지 않는다.
- 초기 웹 피드 노출 범위와 소스별 최대 게시물 연령은 별도 설정한다.

## 11. 패키지 구조

### 백엔드

```
com.whsanha55.feedforge
├── global/
│   ├── config/
│   ├── exception/
│   └── security/
├── external/
│   ├── telegram/
│   └── hackernews/
├── collect/
│   └── source/
├── scoring/
├── feed/
├── feedback/
├── notification/
├── profile/
└── web/
```

- feed: 추천 결과 및 조회
- feedback: 피드백 상태·학습 반영
- notification: 알림 선정·발송 상태 관리
- web: REST API
- profile: 관심도 및 설정 관리

### 프런트엔드

```
frontend/                    # feedforge-ui (Vite + React + TS)
├── src/
│   ├── components/
│   │   └── ui/              # shadcn/ui 컴포넌트 (프로젝트 코드로 관리)
│   ├── features/
│   │   ├── feed/            # 추천 피드 화면
│   │   ├── likes/           # 좋아요 목록
│   │   └── settings/        # 관심도·알림 설정
│   ├── lib/
│   └── styles/              # 디자인 토큰 (CSS 변수)
```

- 서버 데이터는 fetch + TanStack Query.
- 화면 상태는 컴포넌트 로컬, 공유 상태는 가까운 공통 부모.
- 토큰·컴포넌트 규칙은 개인 design-system 컨벤션 준수.

티켓 prefix: FDG

## 12. 마일스톤

먼저 알구더 하나로 수집 → 추천 → 웹 피드백을 끝까지 검증한다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| M0 | 백엔드 스캐폴딩·DB/role·Flyway·인증 + 프런트엔드 스캐폴딩(Vite+Tailwind+shadcn/ui) | 앱 기동·헬스체크·인증 동작, UI 컨테이너 응답 |
| M1 | 알구더 수집·원본 갱신·스코어링·피드 API | 중복 없이 수집되고 추천 근거 확인 가능 |
| M2 | 웹 피드·좋아요/싫어요/취소·학습·관심 키워드 추가(온보딩) | 모바일에서 피드백 가능, 이후 점수에 반영 |
| M3 | 좋아요 목록·관심도 설정 | 제외 키워드·카테고리 가중치·학습값 초기화 가능 |
| M4 | Telegram 선택적 알림 | 상한·조용한 시간·중복 방지·실패 정책 검증 |
| M5 | FM코리아·아카라이브·GitHub·HN | 소스별 수집·추천 정상 동작 |
| M6 | 통계·운영 개선 | 추천량·피드백률·수집 실패 상태 확인 |

M1에서는 실제 알림을 보내지 않는 관찰 모드로
추천 점수와 오탐을 먼저 점검한다.

국내 RSS는 대상 매체가 확정되면 M5 또는 후속 단계에 포함한다.

## 13. 운영 및 보안

### 수집

- 소스별 타임아웃·재시도·요청 간격 설정
- 수집 실패를 소스별로 격리
- 스케줄러 중첩 실행 방지
- 마지막 성공 시각·수집 건수·오류 기록
- HTTP 200이지만 파싱 결과가 0개인 상황 감시
- 파서 fixture 기반 회귀 테스트
- 사이트 이용 정책을 확인하고 차단 시 우회보다 해당 소스 중단을 우선

### 웹 및 데이터

- 웹과 REST API에 인증 적용
- UI와 API 서버 간 프록시 구성에서 인증·CORS 정책 일관성 유지
- 외부 제목·설명 출력 시 HTML escape
- 봇 토큰·DB 비밀번호를 저장소와 로그에 노출하지 않음
- 외부 접근 시 HTTPS 적용
- DB는 내부 네트워크로 접근
- Flyway 마이그레이션 및 DB 백업 유지

### 알림

- 일일 상한·조용한 시간 적용
- 알림 상태별 처리량과 오류 관찰
- 오래된 발송 대기 항목 만료 처리
- 결과 불명확 발송을 무조건 재시도하지 않음

## 15. 초기 성공 기준

첫 검증 목표는 소스 개수가 아니라 추천의 유용성이다.

> 알구더 하나만 연결해도 사용자가 며칠 동안 웹 피드를 계속 확인하고,
> 추천이 자신의 관심에 맞는다고 느끼는가?

확인할 지표:

- 일일 추천 항목 수
- 좋아요·싫어요 비율과 이유
- 중복 딜 및 종료된 딜 노출 빈도
- Telegram 알림의 유용성과 피로도
- 관심도 변경 후 추천 결과의 변화

피드백 비율만으로 만족도를 단정하지 않는다.
무반응은 부정 평가로 처리하지 않으며, 실제 사용 의견을 함께 확인한다.

추천 만족도가 낮다면 소스 확장보다 매칭·중복·신선도·알림 정책을 먼저 개선한다.
